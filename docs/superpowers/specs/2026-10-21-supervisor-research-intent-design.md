# Supervisor application Research Intent

Approved in chat on 2026-10-21: integrate Research Intent into all new student Supervisor applications, across all programmes and courses. Four steps, saved drafts, shared identity/project data and authorised submitted views. Existing approvals, private document rules, capacity, semester intake and Office replacements stay intact.

Implemented and verified on 2026-10-21. Evidence and the one inherited unrelated frontend assertion failure are recorded in `PROJECT_STATUS.md` and `output/research-intent-20261021/`. Draft abstract text has a 10,000-character limit; the existing backend final-submission abstract contract is preserved. Course/proposal steps remain mounted but hidden/inert when inactive to retain local editing state.

## Submission contract

Every new student application POST requires `researchIntent`: a JSON object (or multipart JSON string), exactly `{version:1,introduction,aim,researchQuestions,researchObjectives,significance,methodology,expectedOutcomes,skillsNeeded,timeline}`. Each content value is trimmed nonempty plain text, maximum 10,000 characters. Reject malformed/unknown fields and non-string/coerced values. Preserve the existing title, area and short abstract as shared application fields. The server stores the cleaned intent as a nullable immutable application snapshot; existing applications and Office replacements have null. Never fabricate historical content or change the approved research profile/amendment model.

`GET supervisor/applications/<id>/research-intent/` returns `{researchIntent: object|null}` using the existing exact-application access check. Never add full intent to queues, search, exports or public profile responses. All permitted existing request readers use the same shared detail section, with explicit legacy/missing, loading and retry states.

## Draft contract

Authenticated Student-only `GET/PUT/DELETE supervisor/application-draft/`, no caller student identifier. GET/PUT return `{draft: SupervisorApplicationDraftInput|null, updatedAt: ISO|null}`. One database draft per student, separate from submitted applications and capacity. PUT accepts exactly `{version:1,step:1..4,researchTitle,projectCodeEntries:string[],researchArea,researchAbstract,titleOrigin:''|'STUDENT'|'SUPERVISOR',courseResults:[{courseName,courseCode,semesterSession,grade}],noCoursesTaken:boolean,proposedSupervisorId:string|null,researchIntent:{version:1,...nine text fields}}`. Allow blank/incomplete draft content; validate types, exact keys and existing title/course bounds, max 50 rows and bounded arrays. Do not accept identity/profile data, declaration, status or files. DELETE returns 204. Draft access uses existing Student eligibility boundary; final submission revalidates all existing rules and deletes the student's draft atomically only after successful creation. Draft responses are private/no-store.

## Student flow

Four accessible sequential steps with a progress indicator (not tabs): 1 Your details (authoritative student particulars, contact editor, courses); 2 Research intent (shared title/area/source/course codes/short abstract and the nine fields grouped as Background and purpose / Questions and objectives / Research plan); 3 Supervisor and documents (existing candidate selection and uploads); 4 Review and submit (complete actual research text, particulars/course/selection/file review and fresh declaration). Back/Continue never submit. Validate the current step on Continue, then all steps on final submission; jump to the invalid step and field. A single form must not trigger hidden required inputs. Step controls must work at 390px with visible focus, readable labels and inline errors.

Save draft is explicit, server persisted and permits incomplete content. Load an existing draft with a visible resume/discard choice; never silently overwrite current writing on a late response. Save text and choices only: clearly state files must be reselected when resuming. Do not restore declaration. A saved draft must not reserve capacity, submit or create a workflow status. Keep unsaved-navigation guards, clear dirty only for the exact saved state, and recheck current candidates on restore/final submit. Failed submission retains writing and files. Busy save/submit prevents competing mutations. Do not add dependencies or alter other appointment navigation/shared browse structure.
